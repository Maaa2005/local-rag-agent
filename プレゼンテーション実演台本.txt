プレゼンテーション実演台本
1. 導入：背景と目的（0:00 - 2:30）
【スライド1：表紙】
•	視覚要素： タイトル「完全ローカル型 事務用自律AIエージェント 構築レポートおよび今後の展望」 
（ナレーション） 皆様、お疲れ様です。本日は「完全ローカル型 事務用自律AIエージェント 構築レポートおよび今後の展望」と題しまして、社内業務の効率化を目指した次世代AI基盤構築プロジェクトの全容を報告いたします 。 
近年、生成AIのビジネス活用が急速に進んでいますが、機密情報の取り扱いやセキュリティの観点から、導入を躊躇されるケースは少なくありません。本プロジェクトは、そうした課題を根本から解決するための挑戦です。
【スライド2：プロジェクトの背景と目的】
•	視覚要素： 課題（対応工数の増大、ITサポートや経費申請の頻出） / 前提（外部API一切不使用の完全ローカル環境） / 提供価値（自律型AIエージェント、社内システム連携） 
（ナレーション） まず、本プロジェクトの発足背景と目的についてご説明します 。 現在、私たちの社内では、ITサポートや経費申請といった、いわゆる事務的な問い合わせ対応の工数が爆発的に増大しています 。これらへの対応により、担当者の本来の業務が圧迫されており、負担軽減が急務となっていました 。 
一方で、社内のITインフラや経費に関するデータには、当然ながら多くの機密情報が含まれます 。そのため、ChatGPTをはじめとする外部APIへのデータ送信は絶対に許されません 。 
そこで私たちが導き出した答えが、外部APIを一切介さない「完全ローカル環境」の構築です 。 私たちが目指したのは、単にユーザーの質問に答えるだけのチャットボットではありません 。社内システムと高度に連携し、自律的にタスクを判断して実行できる、次世代型の「自律型AIエージェント」の基盤構築です 。これにより、機密情報を完全に守り抜きながら、持続可能な社内ITサポート体制の抜本的な変革を実現します 。 
2. 技術スタックと実行環境（2:30 - 4:30）
【スライド3：採用した技術スタックと実行環境】
•	視覚要素： コアLLM（Gemma 4 31B） / 学習（LLaMA-Factory、LoRA、4-bit量子化） / 評価・実行（カスタムPythonスクリプト、Linux仮想環境、CLIベース） 
（ナレーション） 続いて、この完全ローカル環境を支える技術スタックと、実行環境についてご紹介します 。 
本プロジェクトの核となる大規模言語モデルには、高度な推論能力と優れた指示追従性を兼ね備えた「Gemma 4」の31Bモデルを採用しました 。この規模のモデルをローカルで効率的に動作・学習させるため、学習フレームワークには「LLaMA-Factory」を選定しています 。今回はLoRA、および4-bit量子化を組み合わせることで、計算リソースを抑えつつも、非常に効率的なファインチューニング、いわゆるSFTを実施できる体制を整えました 。 
また、評価環境としては、人手を介さずに自動でベンチマークテストを行える「カスタムPythonスクリプト」を自社開発しました 。実際の実行環境は、Linux仮想環境上にCLIベースで構築されています 。データセットの準備から、学習、そして自動検証にいたる各プロセスをCLIと自動化スクリプトで繋ぎ込むことで、作業の一貫性と再現性を完全に担保しています 。 
3. アーキテクチャの基本アプローチ（4:30 - 7:30）
【スライド4：アーキテクチャの基本アプローチ】
•	視覚要素： 「AIルーター」を中心とした4つのアプローチ（方針：司令塔、対話：状況深掘り、連携：プラン出力、防御：ガードレール） / ポイント：RAGの前にルーターを介在させる 
（ナレーション） ここで、本プロジェクトの最も重要な戦略である、アーキテクチャの基本アプローチについてお話しします 。 
社内業務にAIを導入する際、まずは「RAG（検索拡張生成）」を作って社内文書を読み込ませよう、と考えがちです。しかし、私たちはあえてRAG構築の事前段階として、AIを「優秀な司令塔」、すなわちタスクの正確な振り分けを担う「ルーター」として徹底的に設計・育成する方針をとりました 。 
なぜか。ユーザーからの社内問い合わせというのは、往々にして「曖昧」だからです。 例えば、「パソコンが動かない」「申請ができない」といった曖昧な指示を、AIがそのまま即座に実行に移したり、システムに連携したりしては、誤作動やエラーの原因になります 。 
そのため、この司令塔AIには4つの役割を学習させました 。 1つ目は「状況の深掘り」です。曖昧な指示に対しては、すぐに動くのではなく、あえて「逆質問」を行います。不足している情報を特定し、ユーザーとの対話を通じて、指示の解像度を学習プロセスの中で引き上げます 。 
2つ目は、情報が十分に揃った段階で、初めて具体的な「実行プランを作成」することです 。 
3つ目は「システムへの連携」です。AIが作成した実行プランは、後続の社内システムがダイレクトに読み取れるよう、厳格な「JSON形式」のみで出力させます 。これにより、人間が介在しなくても、確実かつ安全な業務実行が可能になります 。 
4つ目は「ガードレールによる防御」です。セキュリティリスクのある悪意ある指示を検知して遮断することはもちろん、業務に関係のない私的な雑談や質問に対しては、毅然と、いわば「冷徹に拒絶」する安全機能を実装しました 。 
RAGを構築する前に、この「AIルーター」を1枚挟む。これが、ユーザーの曖昧さを排除し、完全ローカルでの安全性を担保するための、私たちの核となるアプローチです 。 
4. SFTの実践と失敗からの改善（7:30 - 11:30）
【スライド5：ファインチューニング（SFT）の実践と評価】
•	視覚要素： 3ステップ（01モデル学習 → 02評価データ自動生成 → 03自動評価・スコアリング） / 5つの評価カテゴリ / KPI（JSON出力の正確性、指示遵守率） 
（ナレーション） では、この司令塔AIをどのように育て、評価したのか。ファインチューニングの実践と評価のプロセスに移ります 。 
本プロジェクトでは、人手を介さない一貫した自動評価フローを構築し、モデル改善のサイクルを高速化させました 。具体的には、独自に作成した「事務エージェント用」の学習データセットを用いてSFTを実施したあと 、Pythonスクリプトを用いて、5つのカテゴリにまたがる計200件のテスト用評価データを自動生成・スコアリングしました 。 
評価カテゴリは、「ハードウェア/社内IT」「経費精算/セキュリティ」といった実務特化型ナレッジの抽出精度を見るものから、ガードレールが機能しているかを試す「私的雑談」まで、実務に基づいた5つの領域を網羅しています 。 
ここでの重要評価指標、いわゆるKPIは極めてシンプルです 。 後続システムと連携するための「JSON出力の正確性」 、そして、指定したフォーマットをどれだけ守れているかという「指示遵守率」です 。これらを機械的にスコアリングし、現場投入に耐えうる客観的な性能評価を行いました 。 
【スライド6：失敗分析とデータ主導の精度改善】
•	視覚要素： 初回成功率：40% → 失敗原因の分析（過剰な親切心、JSON指定漏れ） → 対策（20件のエッジケース追加、再学習v4、プロンプト最適化） → 成果（大幅な精度向上） 
（ナレーション） しかし、最初からすべてが順調にいったわけではありません。ここからは、私たちが直面した生々しい失敗と、それをどうデータ主導で乗り越えたかという、改善のドラマをお話しします 。 
実は、構築した初期モデルで最初のベンチマークテストを行ったところ、その成功率はわずか「40%」という低い数字にとどまりました 。 
失敗の原因を詳細に分析したところ、非常に興味深い2つの弱点が浮かび上がりました 。 1つ目は、AIの「過剰な親切心」です 。ガードレールで拒絶すべき「非効率な雑談」に対して、AIが良かれと思って親切に応答してしまい、結果として不要な「一人芝居」のような長文の対話を発生させてしまったのです 。 2つ目は、出力形式において、最も重要であるはずの「JSON形式の指定を漏らす」というエラーでした 。 
私たちはこの結果を受け、即座に「エッジケース」と呼ばれる、AIの弱点を突く特定シナリオを20件、ピンポイントで構築し、データセットを補強しました 。具体的なシナリオとしては、「機密情報の社外持ち出し要求への対応」や、「雑談に対する明確な拒絶」、そして「複雑な条件分岐を含む入出力の検証」です 。 
これらの弱点補強データを統合して再学習を実施し、同時にエンジニアリングによってプロンプト構造を最適化した「v4モデル」を作成しました 。このデータ主導のフィードバックループにより、モデルの指示遵守性能は劇的に跳ね上がり、大幅な精度向上を実現することに成功したのです 。 
5. 今後の展望とロードマップ（11:30 - 14:30）
【スライド7：次のフェーズ：RAG（外部メモリ）との統合】
•	視覚要素： Phase 01（現在の到達点：司令塔としてのAI、JSON出力） → Phase 02（次のステップ：RAG統合、ChromaDB、LangChain、社内規程・マニュアル） 
（ナレーション） ベースとなる頑強な「司令塔」が完成したところで、プロジェクトはいよいよ次のフェーズ、すなわち「RAG（外部メモリ）との統合」へと進みます 。 
現在のPhase 01の到達点として、AIはユーザーの意図を正確に解釈し、最適なタスクシーケンスを組み立ててJSONとして出力する能力を持っています 。 
続くPhase 02では、このAIが出力するJSONをトリガーにして、自動検索を実行する仕組みを連結します 。具体的には、ベクトルデータベースである「ChromaDB」を活用し、LLMオーケストレーションツールである「LangChain」を用いることで、高度なシステム連携を実現します 。 
検索対象となるのは、社内規程や各種業務マニュアルです 。AIが持つ「状況に応じた実行プランの作成能力」と、RAGによる「正確な社内知識」をシームレスに結合させることで、実務への即応性を極限まで高めてまいります 。 
【スライド8：今後のロードマップと期待される効果】
•	視覚要素： STEP 01 基盤構築と自動化（RAG、API連携） → STEP 02 安全性と効率の両立（自動起票・承認自動化） → GOAL 自律型AIアシスタント（全社共通インフラ、意思決定支援） 
（ナレーション） 最後に、今後のロードマップと、それによって期待される効果についてまとめます 。 
私たちのロードマップは、情報の「検索」から、システムへの「実行」へとフェーズを移行させていくことに要諦があります 。 
まず直近のSTEP 01として、先ほど申し上げた検索（RAG）との紐づけを完了させ、各種API連携の実装を推進します 。 続くSTEP 02では、さらに踏み込んで「チケットの自動起票」や、社内の「承認フローの自動化」に着手します 。これらをすべて完全ローカルでの動作検証のもとで進め、曖昧なリクエストをも的確に処理できる、セキュアな実行環境を確立します 。 
そして最終的なゴールとして、従業員のあらゆる業務課題を解決する「全社共通の自律型AIアシスタント」へと昇華させます 。 
これにより、社内の事務担当者の作業時間は大幅に削減され、よりクリエイティブな業務に集中できるようになります 。また、単なる作業の自動化にとどまらず、人間の意思決定を高度に支援するインフラストラクチャとして、全社に貢献していく所存です 。 
ローカル環境の圧倒的な安全性を維持したまま、究極の利便性を実現する。この自律型アシスタントの完成に向けて、引き続き開発を邁進してまいります 。

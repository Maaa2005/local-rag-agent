## 1. 範囲

- 少数の既知の規程を、確認済みの構造化記録（以下「記録」）として持つ。索引を作る時に任意の規程から条件を自動で取り出す事はしない。「知らない規程を自動で扱える」とは報告しない。
- 対応する計算は次の 4 つだけ。これ以外は「対応範囲外」として保留する。
  1. 金額の比較: 1 つの金額と境目。単位は円（「万円」「千円」は換算）。比べ方は `>` `>=` `<` `<=` の 4 つ。
  2. 期限の比較: 記録に書いた基準日（発生日・購入日・誕生日など）と期限の決め方（「翌月 N 日まで」「翌日から数えて N 日以内」「指定日より前」など）から期限日を出し、もう 1 つの日（申請日・受診日など）と比べる。月末・年またぎ・うるう年は暦どおりに数える。
  3. 量の比較: 年・ヶ月・日・km・人などの量と境目。単位が記録と違えば保留（換算表を持つ単位だけ換算）。
  4. 割合の比較: 質問に百分率がそのまま書かれている場合、または記録に書いた「分子の役割」と「分母の役割」の両方が質問の中で特定できた場合だけ計算する。「A のうち B」という言い回しだけで割り算を決めない。分母 0 は保留。
- 1 つの規程の条件は 3 つまでの「かつ」で組み合わせる。「または」と入れ子は初版では扱わず、対応範囲外として保留する。

## 2. 記録の形

1 規程 1 件。JSON で持ち、文書の版に結び付ける。

| 欄 | 中身 |
|---|---|
| `rule_id` | 記録の名前 |
| `doc_path` / `doc_version` | 規程の文書と、その本文の SHA-256。索引の文書が別の版なら記録は無効（保留: 規程が更新され、記録が未確認） |
| `evidence` | 根拠の引用（文書に一字一句そのまま在ること）と行の位置。条件ごとに引用を持つ |
| `subject` | 規程が当てはまる対象（例: 経費精算の申請）。当てはまると判定する語と、外す対象（例: 出張旅費は別規程）を持つ |
| `facts` | 結論に要る事実の役割（例: 発生日・申請日・出勤日数・全労働日数・勤続期間）。種類（金額・日付・量・割合）と単位、質問から取り出す手がかりの語 |
| `conditions` | 事実の役割・比べ方・境目・単位。全部が「かつ」 |
| `exceptions` | 規程に書かれた例外・「原則として」の扱い。質問が例外に当たる事情（やむを得ない事情など）を述べたら保留 |
| `other_requirements` | 質問が問うていない別の要件（例: 領収書の添付）。下の 3 節の決まりで扱う |
| `outcomes` | 条件が全部成り立つときの結論と、どれかが成り立たないときの結論。規程から導けない側は `unknown`（保留）にする。成り立たない側を機械的に反対の結論にしない |
| `options` | 質問が求める結論の言い方（例: 必要 / 不要） |

## 3. 決め方（質問 1 問ごと）

1. 既存の権限付き検索で根拠を取る（閲覧レベルは今のまま検索の前に適用）。
2. 取った根拠の文書に結び付いた記録だけを候補にする。版が違う記録は使わない。
3. 対象の判定（コード）: 候補の記録のうち、質問が対象に当たる物を選ぶ。0 件なら「数の規程ではない」としてモデルの通常の回答へ回し、記録に「モデルだけの回答」と残す。2 件以上で決められなければ保留。外す対象に当たれば、その記録は使わない。
4. 事実の取り出し（初版はコード）: 記録の手がかりで、質問から役割ごとの値を取る。同じ役割に違う値が 2 つ以上、役割が決まらない値、単位のずれは保留。
5. 計算（コード）: 条件を全部評価する。どれかの事実が無ければ保留。
6. 結論の選択（コード）: `outcomes` から選ぶ。`unknown` なら保留。
7. 答えの文（コード）: 決まった型で組み立てる。中身は根拠の引用・取り出した値・計算・結論の行だけ。モデルに結論や説明を書かせない。
8. 保留の時は、決めた結論を出さず、理由（どの段で何が決まらなかったか）を返す。黙ってモデルの通常の回答に戻す事はしない。

モデルの役（初版）: 3 で 0 件になった問の通常の回答だけ。事実の取り出しをモデルに任せる版は、後で別の構成として測る。

### 質問が触れない前提の決まり（10/24 に固定）

- `conditions` に入れた事実（例: 有給の「勤続 6 ヶ月」と「出勤 8 割以上」）は全部必要。質問に無ければ保留する。開発用の N07〜N09 は質問に「入社から 6 ヶ月が経過」と書いてあるので、この決まりのままで答えられる。
- `other_requirements` は、記録に「書かれていなければ満たしていると見なす」と明記した物だけそう扱い、答えの文に「（領収書の添付など）他の要件は満たしている前提」と書く。質問が「満たしていない」「分からない」と述べたら保留する。
- 「原則として受理しない」のような書き方は、例外の中身が規程に無い限り、条件が成り立てば記録の結論（受理されない）を出す。質問が例外に当たる事情を述べたら保留する。
- この決まりは新しい問の作り手にも同じ文で渡す。

## 4. 問ごとの判断の記録

答えを作ったその場で 1 回だけ作り、保存する。後から計算し直して作らない。架空データの評価だけで保存し、本番の監査（本文を残さない）とは分ける。

欄: 問 id・使った記録と文書の版・根拠の位置・取り出した値と役割・計算と結果・選んだ結論・保留またはモデルだけの回答に回した理由と段・最終の答え・正誤。

### 7.1 条件と結論の対応（記録の `relation` 欄）

A は数の条件、X は質問が求める結論。記録は原文の文の型を `relation` に書き、表が許す側だけ結論を持つ。許さない側は `unknown`（保留）。

| `relation` | 原文の型 | 結論を持てる側 | `unknown` にする側 |
|---|---|---|---|
| `if_then` | A なら X | `all_true`（A が成り立つ時の X） | `any_false` |
| `if_then_not` | A なら X しない | `all_true`（不支給・不要など） | `any_false` |
| `only_if` | X するには A が要る／A に限り X する | `any_false`（「X しない」） | `all_true` |
| `if_else` | A なら X、それ以外なら Y | 両側 | ― |

- 各側に、対象・別の要件・例外を確かめた上で、その側の引用を付ける。`if_else` の Y 側は、Y を定める文（「上記以外は〜」など）の引用を持ち、X と同じ行為・同じ対象について言っている事。
- 必要条件か十分条件か決められない文は、両側 `unknown` にする。
- 否定で推論する側（`inferred_negation`）は使わない。読み込みで、`relation` が許さない側に `unknown` 以外の結論がある記録は拒む。
- 開発用の答えが合うからといって、表が許さない側を残さない（6 節）。開発用の点が下がっても、そのまま報告する。
- やめる条件: 記録を作る役と確かめる役の判断が割れた記録は、両側 `unknown` にして、扱える文の型を狭める。

### 7.2 未確認の記録は使わない

- 作問役（Codex）が記録を採点し、「可」とした記録だけを確認済みの表（`v2/decide/records/verified.json`）に載せる。表には、記録の中身の SHA-256 と、採点結果のファイルの SHA-256 を残す。載せる道具は、採点の「可」の行しか載せない。実装役が手で表を書かない。
- 評価の設定では、表に無い記録・中身のハッシュが表と違う記録・表が無い時は、起動の時点で止まる（読み込みの誤りとして返し、黙って外さない）。
- F7 の試験: 確認済みの記録から (a) 結論を逆にした物、(b) 境目の数を変えた物、(c) 文書の版を変えた物、(d) 表に無い新しい記録、(e) `relation` が許さない側に結論を持つ物、の 5 つが、使う前に止まる事を確かめる。
- 機械が保証するのは「確認済みの物から変わったら止まる」「表の型に合わない側は止まる」まで。確認役が見逃した誤り（最初から逆に書かれ、採点も通った記録）は保証しない。報告にそう書く。

### 7.3 単位のない量の受け付け範囲

- 記録: 単位のない量の事実の境目の引用に、単位の付いた数（「5点以上」の 5点）があれば記録を拒む。
- 質問から取る数: 数の後ろ（空白を飛ばす）が、文の終わり・句読点・閉じ括弧、または「です／だ／で／と／を／に／は／が／の／以上／以下／未満／より／超」で始まる時だけ、単位のない数として使う。日付・「第〇条」などの番号・単位の付いた数は使わない。
- 上の型に合わない数（カタカナ・漢字・英字が続く「5メートル」「5 点」など）は、手がかりの語と同じ節に在れば保留（単位のずれ）にする。
- 固定の確認例（凍結前に試験として置き、後から変えない）: 引用「5点以上」→ 記録を拒む／「評価は5点です」→ 保留／「評価は5メートルです」→ 保留／「評価は 5 点です」→ 保留／「評価が決まったのは2026年5月1日です」→ 保留／「第7条により、評価は5です」→ 5 で決める（7 を使わない）／「評価は第5条で決まる」→ 保留／「評価は5です」「評価が5の社員です」→ 5 で決める。
- やめる条件: 固定の確認例か受け付ける型の中で、単位や役割を取り違えて決めたら、単位のない量を凍結から外す（その記録は対応範囲外にする）。

### 7.4 判定の接続と判断の記録

- B を測る設定（新しい 96 問を流す道具）は、記録が 0 件・確認済みの表が無い・判定が繋がっていない時は、起動の時点で止まる。
- 判断の記録は、最終の答えが出来た時に 1 回だけ保存する。モデルだけの回答に回した問も、実際の最終の答えと経路を残す。生成に失敗したら失敗として残す。
- やめる条件: 対象の誤一致で、通常の質問を別の規程の結論に変えたら、対象の判定を直すまで B を止める。コードだけの経路に戻して合格扱いにはしない。

### 7.6 「最初の 72 問は答えられる」との食い違い

- 7.1 の表で、最初の 72 問の一部（成り立たない側を問う問など）は答えが決まらなくなる。
- 正解を伏せた再判定（この文書と同じ文で行う）で「導けない」とされた問は、作問役が封の中で正解を「保留」に直し、直した印を問に付ける。結果を見る前に行う。
- 直した問は「宣言した保留」の組として、保留を正解に数え、数を他と分けて報告する。最初の 72 問の他の問の扱いは変えない。
- 再判定と作問役の正解が、どちらも「導ける」のに結論が割れた問は、作問役が理由を付けて直すか、集合から外す（外した数を報告する）。

### 7.7 10/25 追記: 質問が触れない前提（`other_requirements`）の各欄の意味

開発用の記録の採点で、`matters_for` が書かれていないため「その側でしか確かめない」と読まれた（13 件中 4 件）。コードの動きは変えず、今の動きを文にして固定する（`test_other_requirement_holds_on_either_side_regardless_of_matters_for`）。

- 保留はどちらの側の結論でも効く。質問が手がかりの語を「満たしていない」「分からない」と述べたら保留（unmet）。手がかりが無く `assume_met_if_unstated` が false なら保留（unstated）。`matters_for` はこの二つに関係しない。
- `matters_for`（all_true / any_false / both）は、手がかりが無く `assume_met_if_unstated` が true の時に、答えの文へ「他の要件は満たしている前提」と書く側だけを決める。
- 同じ文書の他の条にある承認・期限・書類などの要件は `other_requirements` に入れる。例外（「ただし」「特別な事情」）は `exceptions` に入れ、要件を例外の中だけに置かない。
- 採点役と記録を作る役にはこの節を含む計画の全文を渡す。

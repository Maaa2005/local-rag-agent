# C2（出所で分ける検査）の評価の決まり

Issue #17。合格線の二者協議（11/2・5 段）の結論と、本人の決定（11/3「推奨どおり」）を受けて書いた。封印用を流す前に、この文書のコミットを #17 に書いて固定する。

対象は `judge.provenance_gate.ProvenanceC2Gate`（PR #19）。既定の C2 は `RuleC2Gate` のまま。

## 1. 本人の決定（11/3）

1. 依頼文に入る数値・日付などの自由な値は、前もって承認した値・書き方に限る。外れたら C2 で保留にする（契約 B の送れる範囲を狭める変更）。
2. 承認済みの本文を登録する時は、人が全文を確かめる段を別に足す。

本番への切り替えは、合格の後に別に本人の承認を受ける。

## 2. 集合

開発用 120 件と封印用 120 件。各集合で許可 60・禁止 60。作るのは実装を見ない別担当で、封印用は実装担当に見せない。

| 群 | 許可 | 禁止 | 採点の側 | 中身 |
|---|---|---|---|---|
| 共通語の双子 | 15 | 15 | 依頼文側 | 同じ手がかり語（承認・判定・金額・区分・いいえ など）を許可と禁止で共有する対 |
| 注入 | 15 | 15 | 依頼文側 | 送信審査・判定への働きかけ、指示の無視、制約を外す依頼と、語を共有する対照 |
| 出所の偽装 | 10 | 10 | 依頼文側 | 依頼文に ID・ハッシュ・区分の見出し・JSON を書いて添付や区分を装う物と、その対照 |
| 承認ミス | 10 | 10 | 本文側 | 承認済み本文に禁止情報（個人名・連絡先・実額・実日付）が残る物と、その対照 |
| 組み合わせ | 10 | 10 | 本文側 | 本文も依頼も単独では無害で、組み合わせると禁止になる物と、その対照 |

- 依頼文側は 80 件（禁止 40）、本文側は 40 件（禁止 20）。
- 共通語の双子 15 対に加えて、残りの各群にも、語を共有する許可と禁止の対を最低 5 対入れる。違いは承認の範囲・承認した値・依頼の種類など、判定する側が見られる情報に置く。
- 同じ文型や名前の差し替えを、開発用と封印用に分けて入れない。
- 公開済みの反例（PR #19 の Codex レビューの 22 入力など）は開発・再発防止の試験に回す。封印用には独立に作った例を入れる。
- 封印用の問の番号と並びに正解の規則を持たせない（開発用 120 件は奇数が許可・偶数が禁止で、伏せて解かせても番号で分かった。11/4）。伏せた確認は番号を混ぜた写しで行う。

## 3. 正解の付け方

正解は **送信物（承認済み本文・依頼文・選択値）・承認の記録・契約だけ** から決まる。作った人だけが知る由来（「この数字は実データのつもり」など）で正解を変えない。同じ送信物・承認の記録・契約で正解の違う対は作らない（協議 P1-1）。

契約 B の依頼文は、次を全部満たすときだけ「許可」。どれかを外れたら「禁止」（止めるのが正解）:

1. 契約が禁じる情報を含まない（社内文書の内容、個人名・社員番号、取引先名、金額・日付の実データ、社内のテーブル名・列名・システム名、社内コード、未公開の M&A、指示の注入、送信審査への働きかけ、区分や ID の偽装）
2. 依頼文の自由な値がすべて承認済み（4 節）
3. 依頼文の区切りごとに、依頼の種類（6 節）か、あいさつなどの中立の文に当たる
4. 依頼の種類が、その本文の承認の記録で許した種類だけ

閾値の形の値（「10万円を超える」など）は、承認の記録にある値なら許可、無ければ禁止。

契約 A は依頼文が無いので、本文側の群だけに入る。種類の外の依頼は入れない（設計上は保留になる）。

## 4. 依頼文の自由な値（本人決定の 1）

依頼文から次を切り出す（全角は半角に寄せてから）:

- 数字の並び（`10`・`3.11`・`5,000`）
- 漢数字の値（2 字以上続く物・〇 を含む物。1 字なら後ろに 円・ドル・ユーロ・年・月・日・名・人・歳・割・% が続く物）
- 元号の年（令和元年・平成5年）
- 英字の語（語全体が一覧にあれば可。無ければ `_` で区切った各部分を見る。`total_amount` は `total` と `amount`）
- 引用符（「」『』""“”''‘’）の中身

それぞれ、次のどれかにあれば承認済み:

- **契約の書き方**（`policies/c2_tables.json` の `request_values.B-csv-codegen@1.forms`）。当たった範囲の数字と英字の語は可。
  - 上位・下位・先頭・末尾 N（3 桁まで）／ N 件・行・列・桁・文字・個・回・位・つ（3 桁まで）／ 単独の 0 と 1（後ろに 月・日・年・時・分・秒・%・円・ドルなどの単位が続く物、前後が / - : @ や通貨記号の物は除く。「1月1日」「1/1」「1%」「1ドル」は値）／ N 日・週・か月・年 ごと・単位・間・分（期間）／ UTF-8（-sig）／ Python 3.x ／ YYYY-MM-DD ／ ISO 8601
  - 金額・日付・割合（%）の書き方は入れない。
- **契約の語彙**（同じ所の `identifiers`）。Python・pandas・集計で使う一般の英字の語。大文字小文字は問わない。
- **その本文の承認の記録**（`policies/approved/*.json` の `request_values`）。英字の語（仕様の列名など）と、値そのもの（`10万円` など）。値は出現の範囲にまるごと入る数字だけを許す（`210万円` は `10万円` で通らない）。
- 引用符の中身は、承認した値そのもの、または承認した語・値と区切りの記号だけなら可。

カタカナ語・ひらがな・漢字の語は対象にしない（技術のカタカナ語を前もって並べきれず、誤停止が増えるため）。

## 5. 承認の記録の書き方と、登録への変え方

### 作る人が本文ごとに書く物

| 項目 | 書き方 |
|---|---|
| ID・版・契約・用途・宛先 | 契約の定義と同じ名前で |
| 承認者 | 本文と承認の記録を承認した人 |
| 承知の上で残す箇所 | 本文中の文字列そのままと理由。文字列は本文に 1 回だけ出る長さにする（2 回出るなら前後の語を足す）。外せるのは規程上の額・日付など **実データでない値（金額・日付）だけ**。個人名・社員番号・連絡先・取引先名・社内のテーブル名・M&A・指示の注入は、承認では外せない |
| 許す依頼の種類・禁じる依頼の種類 | 6 節の一覧から。依頼の例を作る前に決める |
| 依頼文で使ってよい値 | 英字の語（仕様の列名など）と、値そのもの（例: `10万円`）と理由 |

例（開発用の架空の本文。`policies/approved/spec-csv-001@1.json`）:

```json
"request_values": {
  "identifiers": ["date", "category", "amount"],
  "values": [{"text": "10万円", "reason": "amount の閾値として依頼文に書いてよい基準額（実データではない）"}]
}
```

### 登録への変え方（固定の手順）

1. 本文と承認の記録を `policies/approved/<ID>@<版>.json` に置く（`request_values` を含む）
2. 許す・禁じる種類を `policies/c2_tables.json` の `combinations` に写す（許す種類も必ず書く。無い組み合わせは保留になる）
3. `python -m judge.c2_registry --write --acknowledge "<ID>@<版>=<本文中の文字列>::<理由>" --checked-by <当たりを承認した人> --reviewed-by <全文を確かめた人>`（`--acknowledge` は箇所ごとに繰り返す）
4. `python -m judge.c2_registry --check` が ok になること

- 正しい記録が登録できない時は、実装の誤りとして数える。
- 記録の欠陥（本文に無い文字列を承認した、など）は、測定の前に確認者が直す。結果を見てから除かない。

### 人の全文確認（本人決定の 2）

- 登録簿の行に、全文を確かめた人（`reviewed_by`）を残す。承認者・当たりを承認した人と同じ人は登録できない。
- **封印用**: 本文を作った人・実装担当・承認者のどれでもない人が、正解を見ずに各本文の全文を読んで確かめる。確認者が見落とした禁止情報は誤通過に数える。**誰が確かめるかは本人が決める（未定）。**
- `fixture:` で始まる確認者は、開発用の架空本文だけに使う。封印用の測定と本番では使えない。替える時は、確認者が全部の本文を確かめ直してから `--write --reviewed-by <名前> --re-review` を流す（`--re-review` が無いと、引き継げる行は前の確認者のまま）。
- 送信時も、登録簿の確認者が承認者と同じなら保留にする（登録簿を手で書き換えた場合の備え）。

## 6. 依頼の種類（細かさ）

契約 B は 8 種類。契約 A は固定の 1 種類（FAQ 整形）。

| 種類 | 意味 | 境目の例 |
|---|---|---|
| 集計 aggregate | 合計・平均・件数・中央値・上位など | 「件数をログに出す」は 集計＋出力 |
| 抽出 filter | 行を除く・抜き出す・絞り込む | 「欠損の行を除外」は 検証＋抽出 |
| 変換 transform | 列を足す・印を付ける・並べ替える・埋める・丸める | |
| 出力 output | 出力・表示・ログ・保存 | |
| テストデータ test | ダミー・サンプル・テスト用データの生成 | |
| 検証 validate | 不正・欠損・型の確かめ・例外 | |
| 説明 document | コメント・docstring・型ヒント・説明 | 11/3 に追加（V016 の「コメントで説明」） |
| 外部通信 network_io | 送信・アップロード・API・URL など | 仕様 spec-csv-001 では禁止 |

- 依頼文を区切り（句点・読点・感嘆符・疑問符・セミコロン・改行と、英字に挟まれていない `,`）に分け、区切りごとに種類が要る。種類にもあいさつにも当たらない区切りがあれば保留。
- ただし、助詞で終わる修飾の区切り（「category ごとに、」「amount が負の行は、」）と、英字の語だけの区切り（列挙の「date、category、」）は、後ろの種類のある区切りに結ぶ。動詞のて形（「読み込んで、」）と「こと・ように・ので・ために」、動詞の言い切り + 「と」で終わる区切りは結ばない（付け足しの依頼になるため）。立場の主張や送り先の語（審査・権限・立場・前提・外部・社外・サーバ・ルール・規則・指示・命令・〜役として）を含む区切りも結ばない（中身を見ずに通すため。11/4 の別の目で 5 件再現）。
- 同じ種類の中で可否を分けたい時は、承認した値（列名・値）で分ける。観測できない意図で分ける対は作らない。
- 種類を足す時は、表とこの文書を同時に変えて版を上げる。

## 7. 合格の条件（全部満たして合格）

1. 封印用 120 件で **誤通過 0**（禁止を allow）・**誤停止 0**（許可を block または hold）
2. 依頼文側 80 件と本文側 40 件を別に採点し、両方で 1 を満たす。止まった理由（内容の検出／承認されていない値／種類不明／未登録・登録の版／区分の形）を分けて残す
3. 故障（例外・タイムアウト・形式不正）0。このゲートは通信しないので、故障は実装の誤りとして別に数える
4. 既存の線を保つ: E2E 39 件を `--c2 provenance` で通し、誤送信 0/22・過剰遮断 0/10・宛先違い 0。V055・V062 は C2 で止まり、V015 は送信される。前段（C1・送信資格・契約）で止まった例は C2 の成果に数えない。#5 の決まり（判定の失敗・形式不正・切り捨ては送らない側）と既存の単体試験は全部通る
5. 添付集合の不変試験（依頼文を何に変えても添付が変わらない）に全部通る

### 0 件の意味

0 件のときの片側 95% 上限は、禁止 60 件で約 4.9%、依頼文側 40 件で約 7.2%、本文側 20 件で約 13.9%。ただし人が作った対の集合で、独立な標本ではない。本番の漏れ率の保証には使わず、「漏れない」とは書かない。

### 補助の指標（合否には使わない）

依頼文側の群だけで、依頼文の語の袋＋ロジスティック回帰（5 分割の交差検証）の AUC を出して記録する。手がかり語だけで解ける集合になっていないかの目安にする。

## 8. 版と進め方

- 開発用 120 件は何度でも使い、手がかり語・語彙・書き方・種類・表を直してよい。直した記録は PR に残す。
- 封印用を流す前に、次を #17 に書いて固定する: コードのコミット、`question_version`、評価用の登録簿と表（封印用の本文と承認の記録を含む）の sha256、この文書のコミット。本番用の版は別に記録し、同じ版を測ったとは扱わない。
- 封印用は 1 回だけ流す。落ちても線を緩めず、流し直さず、封印用で作り込まない。検査のコードか許可リストを変えたら、合格は新しい封印用で取り直す。
- 不合格なら既定の `RuleC2Gate` のまま残す。
- 本番の前に: 登録の取り消しや表の変更は、ゲートを作り直すまで効かない。「送信を止める → 確認待ちを捨てる → 表を直す → ゲートを作り直す」手順を確かめてから切り替える。

## 9. 残る危険（採点から外さない）

止める範囲を広げると誤停止 0 とぶつかる。11/3 に次のように決めた（#17）。

| 穴 | 扱い | 理由 |
|---|---|---|
| 敬称の無い漢字の人名（山田太郎・佐藤の経費） | **広げる**: よくある姓 146 件の一覧（`judge.request_cues` の `person_surname`）で止める。登録時も承認では外せない | 全国でよくある姓の上位から 2 字以上を取り、都道府県名と同じ姓は除いた。このリポの日本語の文書 2,654 行で当たったのは本物の人名の 2 行だけで、ふつうの文を止めた行は 0。開発用の集合から選んだ一覧ではない |
| 一覧に無い姓・名だけ・ひらがなの人名（勅使河原・太郎・やまだ） | **残す** | 名や珍しい姓を並べると、ふつうの語と重なり誤停止が増える |
| 接尾語の無い社名（カタカナのトヨタ・漢字の日立） | **残す** | カタカナ語を許可リストで限ると、技術のカタカナ語を止める。文書のカタカナ語は 393 種類で、半分の文書から作った一覧は残り半分のカタカナ語の 33%（79/237）を知らない。社名の一覧は架空の名前で簡単に外れる。漢字の社名も同じ（11/4 に別の目が指摘・同じ理由で残す） |

- 残した穴は単体試験に `xfail(strict)` で記録してある。封印用の禁止に入っていれば誤通過になり、合格しない見込みがある。
- 本文側の同じ穴は、人の全文確認（5 節）で補う。
- 人名を拾うために形態素解析の人名品詞や固有表現抽出（モデル）を入れるのは、「モデルは送信の判定に使わない」決まりに触れるので再協議が要る。モデル無しの辞書だけで人名を拾う方法の再現率は、公開値が見つからなかった（11/3 の調べ）。

## 10. 調べ（11/3・調べ役 3 体）

- 許可リスト型の入力検査（受け付ける物を定め、外れたら拒否して続けない）: [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)。自由文から値を切り出して許可リストと照合する OSS は見つからず、自作した（近いのは [llm-guard の Regex scanner](https://github.com/protectai/llm-guard/blob/main/llm_guard/input_scanners/regex.py) の許可向きの使い方）。
- 見た目の言い換え: キリル文字・全角記号でメールや電話の検出をすり抜ける実例（[Mimecast](https://www.mimecast.com/fr/blog/5-keystrokes-that-defeat-a-privacy-filter/)）。ラテン＋漢字＋かなは混在とみなさない（[UTS #39](https://www.unicode.org/reports/tr39/)）。それ以外の文字と、ASCII 以外のラテン文字（結合文字で作った Ḿ など）は保留にした。
- 確認者の独立: two-person rule の 2 人目は「1 人目と別人の、権限のある人」（[NIST CSRC](https://csrc.nist.gov/glossary/term/Separation_of_Duty)）。ここでは承認者・当たりを承認した人と別人とし、封印用はさらに作った人・実装担当とも別人にした。
- 0 件の上限は独立な標本を前提にする（rule of three）。人が作った対の集合では上限が見た目より甘くなる。
- 日本語の読点は使い方がまちまちで、区切りに使うと誤分割しやすい。それでも「1 つの区切りに複数の依頼を許す」と付け足しが通るので、読点でも区切り、種類の無い区切りは保留に倒した。誤停止は開発用 120 件で確かめる。

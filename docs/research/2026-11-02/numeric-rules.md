# 小型LLMで数値・日付の条件を正しく当てはめる方法: 文献と実装の調査

調査日: 2026-11-02。対象: local-rag-agent の N テスト（境界値 12 問・合格線 12/12）。
原文は `sources/` に 113 件（1 行目に URL と取得日）。調べ役（サブエージェント）の報告を親セッションが保存した（調べ役はファイルを書けない決まり）。表の細部（各方式の数字・ライセンス・更新日）は調べ役の返信にあり、ここは要点。第三者コードは実行していない。

## 0. 結論

1. 一番効きそうなのは「質問側の値だけを小型 LLM に拾わせ、判定はコード」。今の C の延長。
2. N09 の原因は計算でなく「どの数が分子か」の役割の取り違え。規程側に分子・分母の名前を持たせ、その名前を鍵にして質問から値を拾わせる。
3. 拾い方は JSON schema / GBNF で形を固定（llama.cpp も vLLM も標準対応）。
4. 全角・漢数字・万・割・和暦・日付計算は LLM に任せずコードで正規化。
5. Z3 などへの全面移行は今は割に合わない。
6. 2〜4B で日本語の規程の境界値を測った論文は見つからなかった。

## 1. 失敗の型と文献の対応

- 境界の近くで精度が落ちるのは Qwen3-4B を含む実験で系統的な誤り（Sasaki ほか 2026・arXiv 2606.03982）
- 7〜8B は表記の混ざる数の大小を口で答えると 50〜70%、内部では 90% 超で分かっている（Yuchi ほか 2026・2602.07812）
- TAT-LLM の著者は「比較・数え上げの最後の実行段階で小型が弱い」と書き外部実行器を足した。7B で外すと FinQA 65.13 → 48.47（2401.13223）
- 「同じ種類の値が 2 つ」は GSM-IC（無関係な数字で精度低下・2302.00093）に近い（大型）
- 「コードが決める」試作が 27/96 しか決められなかったのは、質問を読む側までコードで受けたため（推測）。次の案は「読むのは LLM、決めるのはコード」（PolicyGuard・Code-as-Auditor と同じ分け方）

## 2. 主な方式と判定（要点）

## 3. 有望な 5 つと最初の実験

共通: 合格線は測る前に固定。規程側（閾値・比較・式）は規程カードかコードで取り、質問側の値だけ LLM が拾う。結論はコード、確信がなければ今の C に戻す。抽出では thinking を切る。

### 順位 1（試す・本命・費用中）: 規程カード＋制約付きスロット抽出＋コード判定
- 規程カード例: `{種類: 割合, 分子: 出勤日数, 分母: 全労働日数, 比較: >=, 閾値: 0.8}` と定義文 1 行。強いモデルで作り人が確認
- 実行時に json_schema で 1 回だけ抽出。キーはカードの名前: `{出勤日数: integer, 欠勤日数: integer(省略可), 全労働日数: integer, 根拠_出勤: string, 根拠_全: string}`。派生量（出勤 = 全 − 欠勤）はコード
- コードの検査: 根拠の引用が質問に実在・引用の数が値と一致・出勤 ≤ 全・正の整数。通れば割合と比較と結論をコードが決め、説明だけ LLM。通らなければ C に戻す
- 否定の前提（「領収書はありません」）は あり/なし/不明 の 3 択
- 測る物: N 12 問を温度 0 で 3 回、N09 の言い換え各 5 本、既存 96 問と言い換え 24 問で値の一致率、追加の遅れ、派生量の新規 10 問（過学習の確認）

### 順位 2（採る・費用小）: 数・日付の正規化を前処理に
- NFKC → 万・千・億・割・分・％の展開 → 漢数字は Kanjize → カンマ除去 → 単位つきで取り出し。日付は ja-timex か正規表現で日付型にし datetime / jpholiday で計算
- 先に実際に出る表現 50 件の検査表を作り、各ライブラリを手で採点（合格線の案 98%）

### 順位 3（試す・費用小）: PAL/PoT 型と Code Prompting を比較の腕に
- 1〜3 行の式だけを GBNF で絞って書かせ、simpleeval か自作の AST 評価で実行。もう 1 つは規程と値を if つき擬似コードで見せるだけ
- 規程カードに無い派生量の問い用

### 順位 4（試す・費用小）: 一致検査と保留
- 温度 0 の 1 本＋少し上げた 2 本で抽出し、全部一致した時だけコードが決める。崩れたら C に戻す。保留率・保留した中の誤り・確信して外した件数・遅れを測る

### 順位 5（条件付き・費用大）: 合成の境界データで抽出役だけ LoRA
- 順位 1 の値一致率が足りず、プロンプトでも上がらない時だけ。N 12 問とその言い換えは訓練に入れない

## 4. 採らないもの

| 対象 | 理由 |
|---|---|
| Z3 / SMT への全面移行 | 単一の閾値には重い。CoTu は 15 秒に入らない。例外の連鎖が増えたら再検討 |
| Aethis の API | クラウドでローカル原則に反する |
| thinking ありの直接回答 | 手元で悪化。境界の系統的な誤りは考えさせても直らない示唆 |
| CoVe・自己修正 | 外の情報なしの自己訂正は推論で下がる |
| Chain of Code・Toolformer・ToRA・PaD・エージェント系 | 小型で効かない・再学習前提・遅い |
| 関数呼び出し専用モデルへの乗り換え | json_schema で足りる |
| lm-format-enforcer・Outlines・BAML・instructor・DSPy（今は） | llama.cpp の文法で足りる。依存が増える |
| Duckling・JPTextNormTF・jeraconv | 重い／ライセンスなし／停止 |

## 5. 証拠が薄い所

1. 2〜4B で日本語の規程の境界値を測った論文は無い。日本法の数値計算（割増賃金・年休）の評価も無い
2. 小型のスロット抽出で文法制約の有無を比べた厳密な数字が無い
3. PAL/PoT の主な数字は大型。小型は条件が違う（6.7B 再学習・7B LoRA・4B SFT）
4. 自己整合は 20B 以上中心。日付計算の根拠も大型のみ
5. 日本語ライブラリは README だけで未実行
6. 企業発の論文（Aethis・PolicyGuard・ARc）は第三者の再現が無い
7. PDF の表から読んだ数字（Raspanti・TAT-LLM）は列の対応が解釈。引用前に原文の表で確認

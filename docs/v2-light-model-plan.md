# v2 軽量モデル実験計画

作成: 2026-10-19 / 改訂: 2026-10-20（測定前・§7 変更履歴）/ 状態: 実行前（合否の線はこの文書で固定し、測った後に動かさない）

## 0. 目標（2026-10-19 本人決定）

- 最終目標は「学校 PC（GPU 6GB）で動くこと」ではなく、**GPU 8〜12GB の PC で、1 問 15 秒以内に答える、実際に使える RAG**。
- 重すぎると一部の人しか使えないので、蒸留・小型化された賢いモデルを中心に試す。
- 2 つの構成で合否を出す。
  - **下限構成（8GB カード）**: 例 RTX 4060 8GB。ここで通る構成を既定にする。
  - **上限構成（12GB カード）**: 例 RTX 3060 12GB。採る条件は §1「最終判定」。
- 6GB 前提の作業（本番 compose への offload 設定の移植・e886667）は優先度を下げる。下限が 8GB になったため。

## 1. 合否の線（実行前に固定）

候補ごとに G0 → Q → N → P → V の順に見る。G0 で落ちた候補はその先を測らない。

### 合否を読む場所

| 線 | 読む物 | 読む所 |
|---|---|---|
| G0 | `rag_check_result.json` | `ok` |
| Q | `--judge-from` で採点した `report.md` | 総合の表の M7・M4・M6・M8（埋め込み・リランカーを替えたときは M1・M2 も） |
| N | `--dataset evaluation/v2/numeric_boundary.jsonl` で流した `report.md` | 「数値の境目」の節の一致数 |
| P | `--no-judge` で流した 50 問の `report.md` | 「## P 速さ」の節（下の P の表の欄） |
| V | ノートの結果（`gpu_mem_max_mib`） | その実行の間の最大値 |

総合の表の「総合」欄は、P を測った値（T4）の 15 秒で判定している。8GB の P の合否には使わない。

### 失敗の数え方（`evaluation/reporter.py` で実装済・c14cff5）

- **問の失敗**（`run_failed`、または採点以外のエラー）: 分母から外さない。点は 0、拒否すべき問は「拒否しなかった」、時間は ∞ として中央値に入れる。M7 だけは答えた問で見る（失敗した問は文書を何も見せていない）。
- **採点役の失敗**（`judge_failed`）: 回答と時間は残す。総合は「未判定」。採点だけ `--judge-from` でやり直し、回答は作り直さない。
- **無効な実行**: 環境が実行全体を止めた場合（Colab の切断など）。理由を記録し、その実行を丸ごとやり直す。一部の問だけ流し直して差し替えることはしない。
- `--no-judge` の報告の総合は「採点なし」と出る。

**採点役**

- 全候補で 1 つに固定する（済・112e137）。全候補の採点が終わるまで変えない。
- 使う前の確認: 正解の分かっている 4〜6 例（本文どおり・根拠のない断定・数字は同じで結論が逆・一部だけ誤り・拒否）を採点させ、良い答えほど高い点になることを確かめる。通らない採点役は使わない。採点の出力が壊れた問は「未判定」になる（上の失敗の数え方）。
- 人の監査: 最終 2 回の 50 問の答えを人が読み、M4 と食い違う問を数える。食い違いで合否が変わるなら、その候補の採用は保留する。

### N. 数値・境界の正確さ

7/28 の検証で、キーワードが全部入っていても規則の当てはめが間違う例が出た（5,000 円の領収書に「1 万円以上なら部門長承認」を適用）。M6 はこれを拾えない。

- `evaluation/v2/numeric_boundary.jsonl` の 12 問（2026-10-19 作成）: 経費 10 万円を超える→部門長承認（超える）、精算は翌月 10 日まで（まで）、出勤 8 割以上→有給付与（以上）、達成率 80% を下回る→役員賞与なし（下回る）。それぞれ下・ちょうど・上の 3 問。正解は境目の不等号から導き直してテストで照合する（`evaluation/tests/test_numeric_boundary.py`）。
- 答えは 2 択（例: 必要／不要）。質問の最後で「最後の行に『結論: X』とだけ書く」よう指示する。期限は「期限日はいつか」ではなく「受理されるか」で聞く（10/10 と 10月10日 の表記ゆれで落とさないため）。
- 採点は最後の結論行だけを完全一致で見る（`metrics.numeric_conclusion_ok`・`run_eval` で採点済・c2b345c）。本文に両方の語が出ても結論行で決まる。結論行が無い・両方書いた・回答に失敗した問は不一致に数え、分母から外さない。
- 線: **規則の誤適用 0 件**（12/12）。
- N は F7 数値ガードの合否には使わない。N が通っても、ガードが間違った結論を止められるかは分からないため。F7 は間違った結論を入れる別の試験で確かめる。

### P. 速さ

時間は質問を受けた時点から測る（検索込み・`evaluation/timing.py`・916c85d）。

| 指標 | 線 | 読む欄（`report.md` の「## P 速さ」） |
|---|---|---|
| P1 最初の文字までの中央値 | ≤ 5.0 秒 | 最初の文字 p50（P1） |
| P3 8GB: 換算した完了時間の中央値 | ≤ 15.0 秒 | 完了 p50（8GB 換算・8GB の線） |
| P3 12GB: 完了時間の中央値（測定値のまま） | ≤ 15.0 秒 | 完了 p50（測定値・12GB の線） |
| P2 最初の文字までの 95% 点 | ≤ 12.0 秒 | 記録（比較用・総合の表の FTL p95） |
| 8GB 換算で 15 秒を超えた問数・最大 | — | 記録（合否に使わない） |

8GB の換算式（`evaluation/reporter.py:29-35`）:

```
8GB 換算の完了時間 = 最初の文字 + (320 ÷ 272) × (完了 − 最初の文字)
```

- 文章を作る速さはメモリ帯域で決まる。RTX 4060 8GB は 272 GB/s、T4 は 320 GB/s なので、生成の部分（最初の文字〜完了）だけを 320÷272 ≈ 1.18 倍にする。検索と入力の処理（質問〜最初の文字）は計算力で決まり、4060 の方が遅くならない見込みなので、そのまま足す。
- 12GB は係数 1.0（測定値のまま）。RTX 3060 12GB の帯域 360 GB/s は T4 より高いので、測定値は遅めの見積もりになる。
- 換算は予測で、実機で測るまで未確認。4060 より帯域の低い 8GB カードでは 15 秒を超えうる（未確認）。
- 画面へ送る分（SSE など）の上乗せは含めない。`run_eval` はアプリの処理を直接呼ぶため。

### V. GPU メモリ

- 測り方: 実行の間ずっと `nvidia-smi` を 1 秒ごとに記録し、最大値を取る（カード全体の使用量。LLM の重み、実際に使う文脈長での KV キャッシュ、GPU に載せた埋め込みとリランカーを全部含む）。
- 線: 下限構成 **≤ 7,680 MiB**、上限構成 **≤ 11,776 MiB**。カード容量（8 GiB = 8,192 MiB・12 GiB = 12,288 MiB）から 512 MiB を引いた。家庭用カードは画面表示にも数百 MiB 使うため。`nvidia-smi` が MiB で出すので MiB で書く。GB を 10⁹ バイトと読むと 7,153 / 10,967 MiB になるが、測る前の解釈として「カード容量 − 512 MiB」に固定する。
- T4（15,360 MiB）で測るときは、vLLM が先に確保する量を対象カードの予算に合わせる。

  ```
  GPU_UTIL = (予算 − GPU に載せた埋め込み・リランカーの MiB) ÷ 15,360
  ```

  埋め込み・リランカーが CPU のとき 8GB は 0.50、12GB は約 0.76。これは目安で、Step 0.5 で調整を終える。
- 合格の条件（全部）: 必要な max-model-len で起動する／50 問を最後まで流せる／最長の入力の要求が完了する／メモリ不足（OOM）・KV の追い出し（preemption）が出ない／記録した最大値 ≤ 予算。
- 本番の 2 回で予算を超えたら、その実行は不合格。GPU_UTIL を下げ直して救わない。
- T4 で決めた GPU_UTIL の割合を対象カードにそのまま持ち込まない（カードの容量が違うと割合の意味が変わる）。対象カードでは予算から計算し直す。
- 必要な max-model-len = Step 0.5 で測る入力の最大トークン数 + 出力 1,024 を、512 単位で切り上げた値。今のノートは 4096 固定。Step 0.5 のノート（`evaluation/colab/step05_trial.ipynb`）で測って決める（実装済・Colab 未実行）。
- 今の記録はノートで `rag_connection_check.py` を流している間だけ。50 問の実行も記録の中で流す（ノートから `run_eval` を別プロセスで動かす）。`evaluation/colab/step05_trial.ipynb` で実装済・Colab 未実行。
- llama.cpp は vLLM の `gpu_memory_utilization` のような上限を掛けられないので、実測の最大値で判定する。

### 生成の設定と記録

- 全候補で温度 0.1・最大出力 1,024 トークンに固定（`backend/app/config.py:22-23`）。
- seed は送っていない（`backend/app/services/providers/vllm_provider.py:21-22`・未対応）。同じ問でも実行ごとに答えが変わりうるので、最終判定は 2 回の両方合格で見る。
- 実行ごとに記録する: モデル ID と revision、量子化ファイル名、実行系（vLLM / llama.cpp）と版、生成の設定、評価のコミット、データセットの版。`run_eval` の `run_meta.json` に書く（自動の記録と `--meta`。実装済・Colab 未実行）。量子化ファイル名は量子化の候補を測る時に `--meta` で足す。
- 考えるモデル（thinking）: 今は応答の `content` だけを流して最初の文字を測る。考える過程が `content` に混ざるかで「最初の文字」の意味が変わるので、本文の最初の文字までの時間と、生成した全トークン数も記録する。未実装・該当候補を測る前に足す。

### 最終判定

- 採る構成は、別々に起動した 2 回（各 50 問 + N 12 問）の両方が全部の線を通ったときだけ合格。良い方の回や平均で救わない。
- 12GB を採るのは、8GB の最良候補が Q か N で落ち、12GB の候補が 2 回とも全部の線を通ったときだけ。
